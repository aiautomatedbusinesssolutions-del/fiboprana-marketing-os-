# synthesis/

Pattern aggregation across the `observations` corpus. Surfaces what's
recurring so content / product / sourcing decisions get grounded in
patterns rather than the latest single observation. Two layers, both
visible at `/synthesis`:

- **Layer 1** — rule-based SQL aggregations (tag frequency, segment
  breakdown, source breakdown, product-insight rollup). Cheap,
  deterministic, runs on every page load.
- **Layer 2** — an AI synthesis pass that produces narrative pattern
  descriptions with frequency counts, supporting observation citations,
  and "why this matters for Fiboprana" framing. Manual trigger via the
  **Regenerate synthesis** button; output is written to `SYNTHESIS.md`
  at the project root.

## Relationship to existing modules

This module **automates** something that was previously hand-crafted.
The `SYNTHESIS.md` file at the project root has existed since 2026-05-01
and is read as text by the idea proposer (`content/idea_proposal_prompt.py`
references it explicitly). That document was originally generated by hand
and got stale the moment new observations were added.

What's new here:

- A button that regenerates `SYNTHESIS.md` from the current observations
  corpus — no code changes downstream, the idea proposer keeps reading
  the same file.
- A `synthesis_runs` table that preserves every regeneration with
  timestamp, observation count, model, and full markdown output. The
  dashboard renders a run-history list so you can see how patterns
  shifted over time.
- Layer-1 SQL stats (tag frequency, etc.) that weren't anywhere before.
- A drift indicator that flags "the idea proposer is reading
  slightly-stale synthesis" when new observations have been added since
  the last regeneration.

## Routes (registered in `app.py`)

| Route | Method | Purpose |
|------|--------|---------|
| `/synthesis` | GET | Dashboard: headline stats, Layer-1 panels, latest synthesis, run history. |
| `/synthesis/regenerate` | POST | Call Claude with current observations + positioning context; write `SYNTHESIS.md`; insert a `synthesis_runs` row. |

## What the AI prompt does

The cornerstone prompt lives in `synthesis_prompt.py`. It instructs the
model to:

- Read all observations passed in (chronological order, up to
  `MAX_OBSERVATIONS_FOR_SYNTHESIS` in `app.py` — currently 200).
- Identify patterns supported by **≥3 observations** as "top recurring
  patterns." 2-observation signals go under "Tensions"; single
  observations stay as footnotes at most.
- For each pattern: name, frequency, description, supporting observation
  citations with exemplar quotes pulled verbatim, and a "why this matters
  for Fiboprana" paragraph tied to a specific element of the positioning docs
  or PRODUCT_PRINCIPLES.md.
- Identify 2-4 audience clusters and a vocabulary section of verbatim
  user phrases.
- Stay observational — synthesis is for feeding strategy, not
  validating it. Surface tensions with the positioning when the data
  reveals them.

The output is markdown only — no JSON, because the idea proposer reads
the file as text. Match the structure of the existing hand-crafted
`SYNTHESIS.md` (it's the gold-standard reference).

## Cost

Roughly per regeneration with Sonnet 4.6:

- Input: POSITIONING (~3k tokens) + PRODUCT_PRINCIPLES (~3k) +
  observations (~500-1000 each) + system prompt (~2k) → ~20-30k for
  current corpus size.
- Output: ~5-10k tokens of markdown.
- Cost: **~$0.10-0.20 per run**.

Trigger this 1-2x/week as observations accumulate, not on every
observation add.

## Schema evolution

`schema.sql` uses `CREATE TABLE IF NOT EXISTS`, which means column
additions won't apply to an existing DB. Same evolution path as the
other modules:

1. Early (few rows, nothing precious): delete `runs.db` and let it
   rebuild from the updated `schema.sql`.
2. Later: write a short migration script in this folder and commit
   both files.

## Not included (by design, v1)

- **Embedding-based clustering** — finding near-duplicate observations
  worded differently. Powerful but easy to over-engineer; the AI
  synthesis pass handles the same job at v1 scale.
- **Synthesis diffing** — "what changed since last run?" Useful once
  5+ runs exist.
- **Cross-corpus synthesis** — joining observations + captured
  conversations into one pass. Adds complexity; defer until
  conversations table has real volume.
- **Scheduled regeneration** — "run weekly, ping me if anything new
  shows up." Manual trigger is enough for now.
- **Auto-wire into content generators** — the X / TikTok / LinkedIn
  prompts could be fed synthesis output too (not just the idea
  proposer). Defer until v1 is producing useful output regularly.
- **Markdown-to-HTML rendering on the dashboard** — synthesis is
  displayed as preformatted text. Adding a markdown renderer is a
  one-line dependency; skipped to stay stdlib-friendly.
